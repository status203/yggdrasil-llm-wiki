# Forge catalog

Settled decisions, so run-to-run variance does not re-litigate them.

Looked up, not loaded. Facts live beside this in `.yg/facts.md` rather than in it: a script re-checks their version stamps, and a parser has an easier time of a file that is only facts.

## D1 — Where an instruction lives

### D1.1 — route an instruction by what it takes to act on it

**Route an instruction by what it takes to act on it, explicitly not by what it is about.** Topic is the obvious sort and it is the wrong one: it puts every rule about writing prose in one place regardless of what each costs to keep there. The four homes and their order are `forge-mode.md` § *Where a rule goes*.

**The test between 3 and 4 is locality, explicitly not cost.** Cost is the tempting tie-break, since forge mode recurs and the review does not. But routing a writing rule to the review means every session writes without it and the review cleans up afterwards, which is how a corpus grows by review. So cost breaks ties *within* a home, never between 3 and 4.

**Within home 1, enumerable is necessary, explicitly not sufficient: a rule for a rare path that its prose states in a line where it is acted on stays prose, explicitly not a script, a mode or a hook branch because its cases can be listed.** A script, its test and its callers cost upkeep on every change near them, and a hook branch costs a process on every call; on a path met rarely that outweighs the prose's occasional miss, which is the program's opening rule that a mechanism must lower the cost of doing the thing repeatedly. The rule-homes pass was previously observed proposing such scripts run after run, each ignored on this ground.

#### D1.1.1 — a decision's instruction lives in the working file, its reasoning here

**A decision's instruction lives in the file that does the work, its reason there only where the instruction needs it, and all other reasoning here — explicitly not the catalog copy deleted wherever a working file carries the rule, and explicitly not the working file stripped to bare rules.** Deleting the catalog copy strips the rejected alternatives a forge session needs, and without them forge mode and the system review flip-flop the instruction. Stripping the working file removes reasons the running agent uses. A script's header comment counts as its working file, being where the only person who could flip-flop a script decision is already looking, at no context cost outside that edit.

##### D1.1.1.1 — a system-review ignore is settled at the rule it rests on

**A system-review ignore whose reason is a rule that stands is also settled at that rule, its wording narrowed where that rules the misreading out, and an *explicitly not* beside it only where it cannot, explicitly not left only in the record**: passes read the files and never the record, so a reason kept only there brings the place back every run, which was previously observed as a floor of re-raised ignores in every run; an *explicitly not* is read by every reader of the rule and makes it harder to read, so it is the fallback; a declined integration finding is settled at its rule the same way (`D19.1`), and an agreed off-well example carries its mark (`D16.3`). The content review's ignores stay in its record alone, explicitly not written into a subject's files, since no re-raise floor was observed there.

## D2 — How much to build

### D2.1 — a case the program admits is accommodated where a gap fails silently or costs dearly

**A case the program already admits justifies accommodating it where a gap would fail silently or cost something hard to put right, though no wiki has met it yet, explicitly not only a case some wiki has hit, and explicitly not every case that can be imagined.** The program is for other people: a setting it ships or a path it supports is one someone will take, so "no wiki has this yet" describes the person building it, not the program's users, and a gap left on that ground fails silently on whoever arrives first. Accommodating every imaginable case brings back the bulk that minimal-by-default exists to prevent, so YAGNI still rules out what the program doesn't admit. **The form is the one that costs least while unused**, a key defaulting to today's behaviour before new machinery. **Where owners reasonably differ, the default is the safe answer and the owner is asked, explicitly not one answer built in**, since a built-in answer, private or open, is one person's preference shipped to everyone. A gap that shows itself and is easy to fix when met is `D2.2`'s.

### D2.2 — a rare, visible, easily fixed failure gets no rule

**The program doesn't have to be perfect: a failure that is rare, shows itself and is easy to fix when it happens gets no rule, explicitly not a guard written in advance, and explicitly not a script (`D1.1`).** Every rule is read on every run that loads its file, so a guard for a rare, visible case costs more over its life than fixing the case each time it comes up. Previously observed: a run of system reviews whose every fix was a sentence at the place its finding named grew the program by about 1,300 words a fix commit, while the count of serious findings stayed flat. Explicitly not extended to a failure that is silent or costly, which `D2.1` accommodates, nor to the floors in `wiki.md`, nor to a script that fails at what it is for: correcting it costs no reading, since a session runs a script rather than loading it, so it is left only where the fix needs new mechanism for a rare path (`D1.1`).

#### D2.2.1 — an unbranched failure is stopped at and resumed by one rule in `odin.md`

**A step that fails in a way its flow does not branch on is stopped at and resumed by one rule in `odin.md`, explicitly not a branch in each flow, and explicitly not a rule in `wiki.md`.** A flow names the outcomes it designs a response to, a refusal or a *Needs a decision*, and a review a *Failed* or a dispatch that never returned where its coverage rests on it (`D15.2`, `D17.1`); an exit, a *Failed* or a lost dispatch its flow names no response to is rare, and a branch for it in every flow is read on every run for a case that seldom comes. The session running the flow knows the step it stopped at, an agent's *Failed* says what was left unwritten, and the wiki's git shows what a script changed before it stopped, so no component needs a report of its own to be resumed. **The system review raises such a stop only where that cannot recover**: the state it leaves is outside the wiki's git, a step that cannot be undone has run, or the flow carries on past it. Previously observed: about half the edge-case findings of the program's first reviews, each patched with a branch in the flow it named. `wiki.md` is read by every dispatch, which only reports a failure and never resumes a flow.

## D3 — How the program reaches a wiki

### D3.1 — the program is a plugin each wiki enables

**The program is a Claude Code plugin that each wiki enables, explicitly not files symlinked into each wiki's `.claude/`, and explicitly not user-level agents and skills.** A plugin loads in place from the program checkout, so an edit reaches every wiki without a copy to keep in step. User-level agents and skills load in every project on the machine, wiki or not. **Session hooks live in the plugin's hooks file, explicitly not in `.claude/settings.json`**: a wiki session never loads the program's settings.

#### D3.1.1 — rules for every agent arrive by hooks, Odin's by a forced output style

**Rules every agent obeys live in `.yg/wiki.md`, which the plugin's `SessionStart` and `SubagentStart` hooks hand to every session and every dispatch in a wired wiki; Odin's own instructions live in a plugin output style forced with `force-for-plugin` — explicitly not one always-loaded file for both, explicitly not `--append-system-prompt`, and explicitly not a style each wiki selects.** The hooks' context reaches every dispatch, built-in agents included (`F4.5`), and comes back after resume, clear and compaction (`F10.1`), while a forced style reaches the main session only (`F4.3`), so orchestration prose stops costing every dispatch while the floors still reach it. An appended prompt also reaches the main session only (`F4.2`), but needs a launch flag in every wiki; a forced style needs nothing per wiki. **Hooks, explicitly not an `@`-import in each wiki's `CLAUDE.md`**: an import from outside the project loads only once the user approves it in a dialog that defaults to *No* and saves the answer either way (`F3.2`), so setting up a wiki would teach every new user to click through a security warning, while hooks run under the trust given when the program was installed. **Every agent, explicitly not only the program's own**, since the rules bind every agent working in a wiki. The rules arrive in a user turn rather than where `CLAUDE.md` sits. **The style keeps Claude Code's coding instructions** (`keep-coding-instructions: true`), explicitly not the default of dropping them, since the same style applies in forge sessions, where they are wanted.

#### D3.1.2 — how the program root is named

**The program root is named `${CLAUDE_PLUGIN_ROOT}` in skill and agent definitions and `<program>/` in prose read at runtime, explicitly not paths relative to the session, explicitly not a path written into each wiki by setup, and explicitly not a path read from resolved config.** The variable expands only in skill and agent definitions (`F7.4`, `F7.4.1`) and reaches no Bash call's environment (`F7.3`), so the page contract, `wiki.md` and the output style can't use it; an agent's own definition gives it `<program>`, since no `SessionStart` output reaches a named dispatch (`F10.4`, `F4.1.1`, `F4.1.2`) and the rules the `SubagentStart` hook hands one name no path, and Odin reads it from the session-start line (`F4.1.2`). **A built-in agent, which has no definition of ours, gets it in its brief and with none writes no page, explicitly not a path in the hook's context**, which every dispatch receives, Hugin included, and where a home path names the user. **After a mid-session `EnterWorktree`, a session names the wiki root, absolute, in every brief but Hugin's, explicitly not Hugin's too**: Hugin holds web tools alone (`D6.3`), so the root is nothing it can use, and it sends queries off the machine, where a home path names the user. A path written in by setup goes stale when the program moves, and one read from resolved config adds a read to every dispatch. **A forge-only flow names program files by its checkout, repo-relative, with absolute paths in its dispatch briefs, explicitly not `${CLAUDE_PLUGIN_ROOT}`**: through the variable a wiki session could edit and commit the program, forge work `D4.1.2` hands to a forge session, while a repo-relative path finds nothing in a wiki and the flow stops; and a flow that works on a checkout — a diff, a commit — works on the one it runs in, which the loaded program is not in a worktree. **A forge-only agent names them from the checkout its brief gives, explicitly not `${CLAUDE_PLUGIN_ROOT}` and explicitly not repo-relative as a flow does**: a dispatch starts in the launch folder (`F5.1`), and whether one dispatched after a mid-session `EnterWorktree` follows the session into the worktree is unprobed, so only the caller knows which checkout the work is in.

### D3.2 — the wiki folder is the boundary

**The wiki folder is the boundary, and anything Yggdrasil must not read or write lives outside it, explicitly not in private folders inside it.** The wiki may be the whole Obsidian vault or one folder of a larger one. A private folder inside the wiki sits inside the project, so every script, search and agent would have to prune it. **A plugin `PreToolUse` hook, `wiki-boundary.sh`, enforces it: it finds the vault by walking up from the wiki root to the nearest `.obsidian/` — explicitly not any dot folder holding `app.json` as well, though a vault can rename its config folder (`F13.2`): other apps' dot folders hold an `app.json` too, so a home folder would read as a vault and the fence would refuse everything in it, while a renamed folder goes unfenced only once the `.obsidian/` renaming leaves in place is removed — and refuses a path inside the vault but outside the wiki — explicitly not the project boundary alone, explicitly not deny rules written by setup per sibling folder, explicitly not one deny over the vault with the wiki allowed, and explicitly not `permissions.blockReadsOutsideWorkingDirectories`, even for reads alone.** Auto mode reads and writes outside the project without asking (`F12.2`). Per-sibling rules go stale when the user adds a folder, though a `Read` deny would also cover Bash reads (`F12.1`). A vault-wide deny can't be narrowed, since deny beats allow. The read-blocking setting fences no write, and it fences every read outside the wiki, not just the vault's (`F12.2.1`): a file the user points at outside the vault would be refused too, which changes the rule rather than enforcing it, and the hook would still be needed for writes. The hook needs no config and refuses inside dispatches too (`F11.3`). Its Bash check reads paths from the command's words, a heuristic that fences honest mistakes rather than a determined command. **The program's own folder is never refused, should it sit inside the vault, explicitly not fenced as the vault's other folders are, and explicitly not a requirement that the program be cloned outside the vault**: every session and dispatch reads the program's files by path, and where its clone sits is the installer's choice.

## D4 — The forge wiki and forge work

### D4.1 — the program root is itself a wiki, the forge wiki

**The program root is itself a wiki, the forge wiki, explicitly not a `docs/` folder and explicitly not a sibling repository.** **It is named the forge wiki, explicitly not the docs wiki or the program wiki** (user): it holds the docs, the test bed and the reference research, all of it there for work on the program, which "docs" undersold. A session launched in a subfolder also loads the program's forge `CLAUDE.md` and shares its repository, so it isn't what an external wiki is. A sibling repository is a second wiki to keep, and its docs stop changing together with the program. At the root, both kinds of session start the same way, so working on the program exercises the real wiki path. **The mechanism never cites a forge-wiki page**: pages are content, which page-writing rules and content reviews act on.

#### D4.1.1 — every program folder sits inside a dotfolder

**Every program folder sits inside a dotfolder, with `plugin.json` pointing at it, and the forge `CLAUDE.md` is `.claude/CLAUDE.md` — explicitly not program folders at the root hidden by an Obsidian setting.** The program root is the forge wiki, so whatever sits there is a folder of the wiki to Obsidian and to the page scripts. Obsidian ignores a dotfolder entirely, while *Excluded files* still shows a folder in the file explorer (`F13.1`), and components load from dotfolder paths (`F8.4`). The views and checks read only folders holding a `.subject.md` for the same reason, so a folder a wiki keeps for anything else is never indexed, and `move-page.sh` moves a page only into one; its link rewrite still reads the whole wiki, since a link outside a subject still resolves to the page (`F14.1.1`); `check-vault.sh`'s unique-name count, and `regen-views.sh`'s inverted copy of it, read the whole wiki for the same reason.

#### D4.1.2 — the session-start hook decides the kind of session

**The kind of session is decided by the session-start hook — forge when the wiki root is the program root, wiki otherwise — explicitly not judged by the model.** A forge session is a wiki session on the forge wiki with the forge layer on top, so branching on kind stays minimal and forge use proves the wiki path. **A wiki session hands forge work to a forge session, explicitly not doing it with the program added as a directory**: a plugin edit reaches the session running on it at the next `/reload-plugins`, however the plugin is loaded (`F8.3`, `F8.7`), and a wiki session doesn't load the forge method. **A forge session loads the plugin the way a wiki does, from the user-level registration and the forge wiki's tracked, path-free settings line, explicitly not with `--plugin-dir` and explicitly not a local-scope install**: a `--plugin-dir` folder is a protected path, which refuses Write and Edit across the whole project in auto mode, and asks for each in accept-edits (`F8.6`), while a directory marketplace loads the program in place (`F8.7`); a local-scope install writes a machine path into the checkout's own settings and adds nothing a user-level registration lacks.

### D4.2 — forge work is recognised from the conversation

**Recognise forge work from the conversation, explicitly not from an explicit invocation the user has to remember.** The alternative was a skill, `/yg-forge`, on the theory that prose asking a model to remember something is unreliable. It loses on three counts:

- **It is an easy classification, not instruction-following.** Forge work and content work have disjoint vocabulary and disjoint target paths, and classifying them by prose was previously observed never to misclassify.
- **Forge work often is not known to be forge work when a conversation starts.** A content chat can turn out partway through to have a forge component. An explicit trigger is unavailable exactly then, while prose re-evaluates continuously.
- **The asymmetry.** A miss means forge work done without the method, and the program silently gets worse. A false alarm costs one file read in a forge session, or one offer the user declines in a wiki session. So bias toward recognising.

## D5 — Dispatching work

### D5.1 — every dispatch is a named agent, dispatched afresh

**Every dispatch the program makes is a named agent, explicitly not a fork, and a returned one is dispatched afresh, explicitly not resumed by message.** A named agent's definition decides its tools and what reaches its context, and Hugin's web-only safety and `omitClaudeMd` rest on that (`D6.3`); a fork inherits the parent's whole context and tools (`F4.1`, `F5.2`). Resuming a returned subagent is possible (`F5.2`), but nothing needs it yet.

### D5.2 — the agent-authoring standard is its own contract file

**The agent-authoring standard is its own contract file, explicitly not held inside the smith.** Keeping it in Volund looks right, since it is only needed when agents are made. But sessions also write agents directly without loading the smith, and two such agents were previously observed missing what the standard would have caught. A standard only the smith can see binds nobody else. So it sits at `agent-contract.md`, pointed at from forge mode, and Volund reads it like any other writer: the same shape as the page contract. **That includes whether an agent is the right mechanism at all, and that a command in an agent is probed before it ships — explicitly not forbidding commands in agents outright, since agents carry commands their job needs, Mimir's date fetch among them, and a wrong flag is what probing catches; and explicitly not kept in Volund alone**: an agent written by hand never sees what only the smith reads.

**Verification of a forged agent belongs to whoever asked for it, explicitly not to the smith smoke-testing its own output**, which would widen it. A dispatch grant was previously stripped as unused and verification vanished with it. Here it moves to the participant already talking to the user, rather than disappearing.

**Forging and retiring agents is a dispatch, Volund, explicitly not left to the session writing from the contract**: sessions writing agents directly were previously observed missing what the contract catches, and a dispatch holding the contract and briefed with no list of defects previously found every one.

## D6 — Recall and research

### D6.1 — recall is a dispatch over the generated indexes

**Recall is a dispatch over the generated indexes, explicitly not an in-session search and explicitly not a separate projection script.**

- **In-session search, rejected.** The orchestrator is mid-conversation and the map is the whole set of subject indexes. Reading it inline puts all of it into standing context, where `F2.1` charges for it on every subsequent turn of the session, and the lookup blocks the reply it is supposed to enrich. A dispatch is concurrent and, in an interactive session, non-blocking (`F5.4`) and returns a few lines instead of the map.
- **A separate projection, rejected.** `regen-views.sh` already generates the projection recall reads (the wiki's `Index.md` for the subjects, each subject's `Index.md` for its pages and pitches), and a second projection of the same data is a second thing to keep in step. Separate regenerators were previously observed drifting against each other, spelling one escape two ways.
- **The backend is a seam.** `index.query_provider` names it so a fork can point recall at an embedding index or an MCP tool without editing shipped mechanism. The dispatch is the default, not the contract.

**Recall inherits the session's tier, explicitly not a cheaper pin**, though it is the highest-frequency dispatch and its matching is shallow. `agent-contract.md` § *What it may hold* holds the rule and its reason (`F6.2`).

#### D6.1.1 — classification rides on the recall dispatch

**Classification rides on the recall dispatch, explicitly not on a second agent and explicitly not on the orchestrator alone.** `odin.md`'s *name the subject* had no backend, the same gap *look while you answer* had before `D6.1`. A second agent was the obvious shape and earns nothing: it would read the same files, hold the same read-only posture and fire at the same moment, and the agent contract would ask what boundary it draws that the librarian does not. The orchestrator alone was the other option, and it fails on the close calls — the boundaries live in each subject's `.subject.md`, which is a dispatch's business rather than standing context. So one lookup answers both questions. The recall narrowing *was already the classification*, computed as step one and thrown away.

**Where similar material sits outranks a subject's boundary prose, except where the file says the boundary is not topical, explicitly not without exception and explicitly not left unwritten until a misplacement is seen.** Neighbours are what the wiki does, which beats what a description says for a topical subject; for a subject kept together by provenance or purpose, every neighbour points away and only the file knows better, and the misplacement that rule causes is silent, so waiting to see it may mean never seeing it. Placement in the content review weighs the same way (`D14.4`).

**The orchestrator picks one and reports one, explicitly not the ranked list put to the user as a menu**: it re-ranks against the conversation the dispatch never saw. **The brief carries the topic and the conversation's framing of it, explicitly not a summary of the conversation**, since a summary puts the judgment on the summarising (`D10.1`).

### D6.2 — freshness is a gate on the regenerator at session start

**Freshness is a gate on the existing regenerator, run from `SessionStart`, explicitly not a background refresh, explicitly not a pre-commit hook, and explicitly not the librarian regenerating before it reads.** `D6.1.1` leans on the generated indexes, so a stale one makes the narrowing wrong before any page body is opened. Three shapes were available. **A pre-commit hook** fires after the reads that staleness spoils — it fixes the commit, not the lookup. **A background refresh** is safe, since the regenerator's `publish` is atomic and a reader sees old-or-new rather than torn, but it races the dispatch, and losing that race returns a false *nothing found* with nothing signalling it. **A gated synchronous regen**, `regen-views.sh stale`, rewrites only the views whose sources outran them, and its `Cost:` line measures it nearly flat in pages — so the common case is below noticing and the cost tracks the edited subject rather than the wiki, which is what scales to a larger one. It runs from the plugin's `SessionStart` hook, so every session kind gets it. The librarian's bounded worst case, a false return and no more, rests on it holding no execute. **A subject view whose pages changed during its own scan takes the scan's start as its stamp, so the next `stale` redoes it**: explicitly not every view stamped at its scan's start, since `publish()`'s rename lands the directory after that start and every subject would then read stale on every run, and explicitly not regenerated again at once, since a page whose mtime lies in the future would keep it looping.

### D6.3 — research is a dispatch holding web tools and nothing else

**Research is a dispatch holding web tools and nothing else, explicitly not an in-session search and explicitly not a researcher that can read files.** The dispatch half is `D6.1`'s ground. The web-only half is `hugin.md`'s injection triangle, held by its `tools:` list (`F6.1`). **Hugin sets `omitClaudeMd`, explicitly not inheriting the user and project `CLAUDE.md`**: without it the user's own `CLAUDE.md` sits in a context that reads untrusted pages and can send data out in a URL (`F4.4.1`). `wiki.md`'s floors still reach it through the hook (`D3.1.1`), and the ones that apply to a web-only agent are in its definition as well. The fetch tool's own summarising is no substitute for Hugin paraphrasing, because a page has been seen to skip it and arrive verbatim (`F9.1`).

#### D6.3.1 — local material travels in the brief

**Local material travels in the brief, explicitly not through a file grant.** Where research needs a file read, that half goes to a dispatch holding no web tools, so no one agent holds both. The cost is a second dispatch.

#### D6.3.2 — no question field

**No question field, explicitly not a question returned for the session to answer**: a named dispatch cannot ask mid-run (`F5.2`), so a question costs a round trip that brings back nothing. The likelier-case answer hands the session the same fork with something already in it.

#### D6.3.3 — the trigger lives in the agent's description

**The trigger lives in the agent's description, explicitly not in `wiki.md`**, which is charged every turn and every dispatch (`F3.1`, `F4.5`). An auto-mode session was observed dispatching Hugin with no web call of its own. If a session is seen searching inline, an `odin.md` line is the fallback.

#### D6.3.4 — built-in web tools, with no provider seam

**Built-in web tools, explicitly not a third-party search API and explicitly no provider seam.** They cost nothing, and an external API runs against the user's privacy and cost positions. It has none yet; search is model-called, so when it gets one it is an MCP tool named in config (`D20.1.2`). **No shipped `WebFetch` allow rule**: the person running the system decides that.

### D6.4 — a web source is cited as an external link, not archived

**A web source is cited as an external link under `## Sources`, explicitly not archived into `.sources/`.** **Link rot is out of the program's scope, explicitly not a gap left until a wiki meets it**: protecting web citations is for an approach outside the program, chosen by whoever runs it, and `check-vault.sh` skips scheme-prefixed targets. Citations made before access dates were required are not swept, since the dates cannot be recovered.

#### D6.4.1 — a session record keeps each web source's full URL and Hugin's marks

**Where a session record is written, it keeps each web source's full URL and any mark Hugin put on a claim, explicitly not a URL clause in wrap's Bragi brief, and explicitly not a marks line in Hugin's description**, which every session pays for. With no record, the Bragi brief carries them itself (`D10.6`), since nothing else does. The page is written from the record, so a bare site name leaves nothing to follow and a dropped mark arrives as settled fact. Both losses were observed at the session's write of the record. Whether the record line alone carries the URLs is still unseparated.

### D6.5 — Odin's reply keeps Hugin's marks, and Tyr carries them onto findings

**Odin's reply keeps the marks too, in plain words, explicitly not left unmarked because a chat turn doesn't persist, and explicitly not a change to Hugin's return**: the user acts on the reply, and the flattening was previously observed in the session's retelling, five runs in five, with Hugin's return marked. A review over Hugin's items hands Tyr each item's mark, and Tyr carries it onto every finding drawn from the item, explicitly not a mark field in each review's finding fields: one rule in `tyr.md` covers every such review. A staleness walk previously observed losing the mark was the session's retelling, with Tyr's findings marked.

## D7 — Putting content into the wiki

### D7.1 — integration is a dispatch that reads the contract

**Integration is a dispatch that reads the contract rather than restating it, explicitly not a write made in the session.** The material comes from the conversation, so the orchestrator has to hand it over; everything else the write needs — the contract, the target page's whole body, a template — is bulk the session would otherwise carry for the rest of its life (`F2.1`). A dispatch reads it once and returns a few lines, and being non-blocking in an interactive session (`F5.4`) is what makes `odin.md`'s *write first, show afterwards* honest rather than a pause mid-conversation.

**Two dispatches that write the same page never run at once, a rule for the session in `odin.md`, explicitly not a note in each flow that dispatches writers.** An edit applied over another dispatch's change to one page can leave text neither meant, with only a note, where a whole-page write is refused (`F5.5`), and the pairings are open-ended — two items for one page at wrap, a correction beside new material, two writes mid-conversation — so a per-flow note misses the flow not yet written. A flow still names the pages its own writers share, which the session can't tell from their descriptions, or sends each write only once the last has reported, as the staleness and content reviews do. Where the material for one page is known together, it goes in one brief, explicitly not one dispatch per item sent in turn: one brief hands the writer the whole picture for that page, and costs one dispatch rather than a wait on each. Items that are separate operations of the writer's — Mimir's replacement of one step, a fold-in beside a plan revision — go in turn, since a brief carries one operation. A writer that would redirect material onto a page another dispatch is writing returns it as a decision instead, since the session cannot see a redirect coming.

**The agent does not restate `.yg/page-contract.md`.** A second copy of the join rules is a second thing to keep true, and the failure it protects against is silent — the two drift, the agent follows its own copy, and a discussion page gets paraphrased. It reads the contract, and its own definition carries only what the contract cannot know: that it is dispatched, what the brief hands it, and what it must return.

**The named target is a proposal, explicitly not an instruction the integrator executes**, because placement judged from a pitch loses to placement judged from the page body. `bragi.md` § *The target is a proposal* carries the rule and its reason.

#### D7.1.1 — transcribe writes its placeholder page itself

**Transcribe writes a placeholder page itself, explicitly not through Bragi.** There is no existing prose to rework, no join behaviour to choose and no judgment about placement, the page being by definition absent; and handing an integrator a transcript pointer invites it to open the transcript, pulling untrusted text into a context holding Write. On the page route, which needs an integrator, Bragi is handed the kept path to cite with its brief forbidding the open, explicitly not the transcript's text.

#### D7.1.2 — a collision the session cannot order is caught by the writer that edits second

**A collision the session cannot order — another session's writer, the user in Obsidian, two redirects onto a page no brief names — is caught by the writer that edits second, from Edit's modified-on-disk note (`F5.5`), and handed back to the session as a failure, explicitly not prevented by a per-page lock taken before editing.** Stale claims from a dispatch that never returned (`F5.3`) can't be told from another terminal's live ones, so a lock clears only by age, and the user in Obsidian takes none. Caught, the collision is rare, shows itself and is put right by hand (`D2.2`). Where Obsidian saves second, no writer sees it; Obsidian reloads an open page changed on disk (`F5.5`), so only typing at the moment of a write is exposed, and that is left, explicitly not guarded, since only a lock could catch it and Obsidian takes none.

### D7.2 — a source is committed before the page that cites it

**A source is committed before the page that cites it, explicitly not the reverse, and as a general rule, explicitly not per flow.** Cite-first looks safer, a dangling link being louder than an orphan source. But `check-vault.sh` reports both, and it runs as one of the page contract's after-writing steps, so cite-first makes it report a finding on every successful run, destroying the signal. That follows from the checker, not from any flow, so it holds for wrap, transcribe and anything written later. Where the integrator cites the source, the order is not even available, since the after-writing steps run inside its own write. Framed per flow, it was previously re-argued three times and twice landed on the opposite.

### D7.3 — how new material joins a page is set by a list

**How new material joins a page is set by a list — the page contract for project types, the subject's `.subject.md` for a subject's own — explicitly not by templates, and explicitly not every type's rule moved into its template.** Every type has a join rule of its own, while most share `default.md` as their skeleton, so rules held in templates would mean templates written only to carry one, concept's rule landing in the role-named fallback, and a template read before every integration where `.subject.md` is read already. And a template's meta-text is read only as a page is made from it, and removed then, so a rule held there reaches no later edit. **Placeholder and tombstone stay separate types, explicitly not one type with the kind marked in the body**: their join rules are opposites, one replaced wholesale and the other never, and `type:` is what the list keys on, so a kind marked in the body would leave the choice to a read of the page.

### D7.4 — a wikilink is written bare

**A wikilink is written bare, explicitly not subject-qualified.** Every form resolves and renders exactly as written, so the choice is about rendering. A qualified link tells a reader in a text editor or a GitHub view where the page lives, but it buys that source legibility with rendered legibility, and the vault's primary read surface is Obsidian. **Qualified-plus-alias is the alternative to expect back**, since configuring the editor to emit it sounds tidy. But no `newLinkFormat` value writes a subject-qualified link (`F14.3`), so the form would be hand-maintained on every link forever. Where the Obsidian vault is the wiki root itself, as for the forge wiki, the editor's absolute form *is* subject-qualified, but bare stays the rule there too, for one rule across wikis and for rendered legibility. **`check-vault.sh` reports a qualified link to a page whose name no other file in the wiki shares, in any letter case (`F14.2`), explicitly not a link starting with a vault folder's name**: the editor's form starts with a subject where the wiki is the vault and with a folder of any name where it sits inside one, so no prefix tells it from a deliberate path, and only a unique name says the path is unneeded. **Unique is judged among the wiki's files outside a dotfolder, explicitly not the vault's**, since nothing outside the wiki folder is read (`D3.2`): where the wiki sits inside a larger vault, a name it shares only with a page outside it would be reported, and written bare may resolve there (`F14.1.1`), so there a qualified link is not reported. **Where the awk in use does not fold a letter outside ASCII (`F19.3`), a name holding one is left off the unique list, explicitly not reported**: a twin by case in that letter would go uncounted, and the row would say to write bare a link that may be ambiguous. A generated view or other machine file (`role: derived` or `instruction`) is not read, explicitly not held to the bare rule: it is not a page, and nesting is why the regenerator writes paths (`F14.1`). **A view links a page by its path from the wiki root where its name is off that unique list — shared in any letter case, or holding a letter outside ASCII the awk in use does not fold — explicitly not bare**, since a bare link there may open the twin (`F14.1.1`, `F14.2`); the regenerator counts as `check-vault.sh` does, inverted, explicitly not a count of its own, so the two agree on which link may be bare, save in a wiki inside a larger vault, where the regenerator still writes a unique name bare, explicitly not by path: the Docs state the limitation, and the case is rare (`D2.2`). Stamped against Obsidian as the read surface: a fork read primarily somewhere else may revise it.

**Tutorials are written by a dispatch that plans and writes its own pages, explicitly not a tutor skill run in the session and explicitly not an agent owning every progression.** A step is a written lesson read in Obsidian, with conversation after it, so writing one needs the conversation's outcome rather than the conversation; a skill would hold each step's inputs and text in session context (`F2.1`) and block while writing. Practice and companion pages are ordinary integration, so an agent owning them draws no boundary Bragi doesn't.

**Mimir writes its own pages, explicitly not through Bragi**, though elsewhere whoever produces content does not place it. Writing or correcting a step means reading the tutorial as a sequence, which is teaching judgment, not integration. This is explicitly not grounded on context cost: a step handed to Bragi as a file stays out of the session too. Splitting writer from placer was previously observed letting the integrator rework a step's prose as it merged.

**The short pedagogy rules stay written though the current model follows them unprompted** (a step's length band, its opening and closing, a gloss on first mention), because a behaviour one model shows unprompted is not one a later model keeps. **Explicitly not carried:** a three-level learner scale, adaptive fading, a recap at each step's head, a calibration question the system asks, and tightening on feedback about asides.

Guidance with no unwritten step left to carry it, every planned step written or the tutorial finished, gets no rule, explicitly not a wrap branch: it is rare enough for the user and the session to settle by hand. **A fold-in on a finished tutorial records no learner note, explicitly not a curriculum recreated to hold one and explicitly not a note on the recaps page**: notes steer steps still to come, and a finished tutorial has none.

**The trigger lives in the description**, on `D6.3.3`'s ground.

### D8.2 — the three progression kinds stay distinct

**The three progression kinds (tutorial, companion, practice) stay distinct, explicitly not merged.** Who supplies the substance (the system, an external source or the user) decides whether an agent writes the page and how material joins it. `page-contract.md` § *Progressions* holds the rules.

## D9 — Managing subjects, and moving pages

### D9.1 — structural change to the vault is initiated by the user

**Structural change to the vault is initiated by the user, explicitly not inferred from the material.** The vault is the user's working environment, read and edited directly. A reorganisation they did not ask for moves where they look for things, and arrives as a diff nobody reads. The system makes the case; the user makes the call. A test a session could apply, set beside the procedure for acting on it, turns a referral into a licence, so the contract states the gate before the mechanics.

**The lifecycle is stated in the page contract, explicitly not built as a flow and explicitly not left to inference.** The mechanical half (a directory, a subject file, moves, a regenerate) is what a flow would only restate. The judgment half, what makes a boundary, when a cluster stops being one, and which of a subject's types get a template, is what the contract carries.

**Wikilink resolution is deliberately not checked, explicitly not a check added to `check-vault.sh`.** The program's routes that break wikilinks go through `move-page.sh` before the break: a move and a rename rewrite them, the deletion that ends a merge repoints them with `--merge`, and any other deletion lists them for the user with `--links`.

### D9.2 — a move or rename the program makes is one script

**A move or rename the program makes is one script, `.yg/bin/move-page.sh`, explicitly not `git mv` with `check-vault.sh` behind it, and explicitly not a rename in Obsidian.** **The person may still move a page in Obsidian, explicitly not told to go through Odin alone**: out-of-band changes will happen, and what an Obsidian move misses when it updates links — the page's links into `.sources/` and its sidecars — `check-vault.sh` reports. The checker reports a broken relative link after the fact rather than preventing it, and cannot see whether a wikilink resolves. Obsidian's rename rewrites links only where the person accepts its prompt or has turned the setting on (`F14.4`), and a contract naming a tool fails whenever a rename is asked for outside it. A rename is a move with the folder unchanged, so one script carries both: a second copy of the link rules would drift, as separate regenerators were previously observed doing (`D6.1`). **A merge's inbound links are the same script's `--merge` mode, explicitly not a script of its own**: the merged-away page's links break as a rename's do once it is deleted, and a second copy of the rewrite would drift on the same ground. **A deletion lists them with `--links`, which changes nothing, explicitly not left to the deletion floor's prose (`D1.1`)**: the floor asks for them on every deletion, so the session would otherwise re-derive the matching each time, and a second copy of it would drift from `--merge`'s.

**Each half fails silently in its own way, which is what the script is for.** Renaming breaks every inbound wikilink, because the filename *is* the link target, and nothing checks that a wikilink resolves — so a partial rewrite looks exactly like a complete one. Moving breaks every relative link the page carries, source citations included, because those resolve by path and the depth changed, and the editor shows nothing because the target is off the link graph. `check-vault.sh` catches the relative half afterwards, and nothing catches the other. A bare wikilink survives a move, resolving on the filename; a path-qualified one does not, so the script repoints it at the new folder. **A sidecar is named for its page** because that is the pattern the script carries with the page; one named otherwise is left behind by a move. **`check-vault.sh` reports an `.html` file in a subject folder not so named for a page in its own folder, explicitly not left to the broken link it reports after a move, and explicitly not judged by which page links it**: the link row comes only once the page has walked off, and a link is not enough to own a sidecar, since two pages may link one file.

## D10 — Ending a session

### D10.1 — wrap runs in the session

**Wrap runs in the session, explicitly not as a dispatch.** Everything else that touches the wiki is a subagent, so the shape is worth stating: what wrap decides about *is* the conversation, and a named dispatch inherits none of it (`F4.1`). A fork dispatch would inherit it, so running wrap's judgment in one is possible, but nothing needs it yet. Handing a subagent a summary of the session would put the judgment on the summary rather than on what happened, and the summarising is the hard part. So wrap stays in the session, and hands the placing to Bragi once the decision is made — which keeps the roster's split intact, since deciding what is worth keeping was never the integrator's job. **Work still running at wrap, a background command as well as a dispatch, is put to the user first, explicitly not with what ending the session does to the command**, which no fact records.

### D10.2 — integration happens at wrap, because the save bar cannot be applied earlier

**Integration happens at wrap because the bar cannot be applied earlier, explicitly not because end-of-session is more convenient.** The bar is Odin's save bar, *what the conversation settled, or a question the user asked and got a substantive answer to, that the user would want to find again later* (`D10.3`), and mid-conversation nothing tests it: while the conversation is still moving, a conclusion and a way-station look alike, and no automatic test for settledness was found on either pass at this question. End-of-session is the one point where the judgment is free, because the conversation is over and whatever it settled has settled. The costs either way are asymmetric, which is what makes biasing toward the end safe rather than merely cautious. Writing early restructures a concept page's prose around a way-station the conversation then supersedes — silent, and undone only by hand. Waiting costs wall time and some fidelity: at wrap the integration runs while the user waits rather than overlapping their thinking (`F5.4`), and material from early in a long session is reconstructed from a thinner record. Both of those are visible and bounded, which the prose damage is not. So mid-conversation integration is the exception, taken when the user has visibly settled something and moved on; wrap is the rule.

#### D10.2.1 — *write first, show afterwards* makes no timing claim

**Odin's *write first, show afterwards* makes no timing claim.** It is a permission and reporting rule, and it governs any write, including those wrap dispatches. It has been read as a licence to integrate mid-conversation, in one verification run in three, and was left alone, **explicitly not a timing clause in Bragi's description**, because an occasional wrong mid-conversation write is trivially reversible. The clause is the fix if it becomes frequent or does damage.

### D10.3 — the save bar keeps what the user learned, and leans to keeping

**The save bar keeps what the user learned whatever it came from, and leans to keeping, explicitly not judged on whether the answer could be asked for again, explicitly not dropped for having no source, and explicitly not a bar that leans to dropping.** The wiki holds what its owner learned independently of the service they learned it through, so an answer from the model's own knowledge counts as much as a sourced one, and a question the user asked is the evidence of interest. Sessions were previously observed, repeatedly, deciding at wrap that nothing was worth keeping when the answer came from the model, giving that as the reason. The two failures are unequal: a page the user didn't want is reported and removed in a moment, while a dropped answer leaves with the conversation. **Size is weighed only where no page holds the topic, explicitly not as a bar of its own**: a small point folds into a page it belongs on at little cost, while a page started for it alone is thin, a cost every lookup and review pays; **explicitly not a page of unrelated facts**, which nothing curates, since `Misc` is already where material waits for a home. So the wiki lookup at wrap is never skipped, and **every candidate not kept is named in wrap's report**, so a drop the user would overrule is seen while they are there. **One the user keeps after the report is the conversation carrying on, explicitly not a step of wrap's**: the session places it as anything the user has settled, and the user wraps again to commit it (`D2.2`). **Material from the model's own knowledge is cited per page as unchecked, naming the model and the date, explicitly not marked per claim**: a page merged across sessions and research cannot say which sentence came from where, and connective prose from the model is in every page, so only substance the session attributes to the model earns the entry. A claim the session was unsure of still keeps that doubt beside it, as one Hugin marked does, since the page's entry says where the material came from and not how sure it was. An answer given from memory was previously observed wrong on its central claim, which research then corrected. Whether such an answer should go to Hugin as it is given is held in a forge ledger, explicitly not built until skipping it is seen to cost.

### D10.4 — the trigger is wrap's description, backed by `odin.md`

**The trigger is wrap's own description, backed by a clause in `odin.md`, explicitly not the user remembering `/yggdrasil:wrap`.** A skill's description is auto-surfaced into a session while its body is not, and wrap's says to use it when the user says they are done; but compaction drops the skill listing, and a 200K-token window lists skills without descriptions (`F3.1.1`, `F3.1.2`). After a compaction, a session previously observed answering "I'm done" by applying the save bar itself, never running wrap. So `odin.md`'s save-bar sentence names wrap and when to invoke it, since the output style is sent again after compaction and a skill the listing dropped is still invoked by name (`F3.1.1`), **explicitly not a `SessionStart` hook on compaction**, which would carry the same line on a new hook branch, and **explicitly not `wiki.md`**, which every dispatch is charged for though only the session wraps. Its gap is a session ended by closing the terminal, which nothing catches, **explicitly not closed by an exit hook**: whether a conversation holds anything worth keeping cannot be decided mechanically, and a write the user disagrees with is theirs to reverse while the session runs, never once they have left.

### D10.5 — a session that wrote nothing saves no source

**A session that wrote nothing saves no source, explicitly not a record kept every session on the theory that storage is cheap.** An uncited source is a defect a later review has to find, so the cost is maintenance, not bytes.

### D10.6 — a session record goes into a private wiki under `on`, a public one only under `always`

**A session record is written into a private wiki under `on`, and into a public one only under `always`, explicitly not governed by a key per session kind, and explicitly not never in a public wiki**, which built in that no owner wants the conversation published, where an open project may (`D12.2`). A public wiki publishes everything in it, a record included, so `on`, the default, keeps the record out of one. **With no record, the Bragi brief carries each web source's URL, access date and mark itself**: `D6.4.1` keeps them out of the brief only because the record holds them.

#### D10.6.1 — a page integrated mid-conversation is brought to the record by a correction brief

**A page integrated mid-conversation is brought to the record by a correction brief to Bragi, explicitly not by the session editing it.** Wrap writes the record and then hands it to Bragi to cite, so a page written earlier, the exception above, is never reached by it, and carries the access date Hugin stated rather than the record's fetched one. The session editing the page itself works without the page contract, the bulk `D7.1` keeps out of the session; that was observed once, and the result conformed by luck.

### D10.7 — wrap makes one commit in the wiki's repo, staging the whole tree

**Wrap makes one commit in the wiki's own repo, staging the whole tree — explicitly not separate content and system commits, and explicitly not staging by explicit path.** A wiki is its own repo and the program another, so no commit can mix them and no staging script is needed to keep them apart. Hand-picked paths miss what the work produced without writing it, such as a regenerated index; sessions were previously observed reconstructing a pathspec from memory and staging nothing or half the tree. A whole-tree stage can sweep in another session's uncommitted work, typically one that did not wrap, so wrap checks what staged against its own work and names anything else to the user before committing, explicitly not committing around it. The content review, the staleness review and transcribe carry no forge-session clause, explicitly not one naming uncommitted program changes, which their check of what staged against their own work already names.

### D10.8 — wrap pushes only where `wrap.push` is `on`

**Wrap pushes only where `wrap.push` is `on`, off by default, explicitly not always and explicitly not never.** A push sends the wiki off the machine, and nothing generic can tell a private remote from a public one, so pushing waits on the user's say-so; but a wiki with a private remote is otherwise one forgotten `git push` from losing work to a dead disk, so the user can turn it on per wiki or for every wiki.

### D10.9 — in a forge session, wrap does not run

**In a forge session, wrap does not run, explicitly not placing forge-wiki material.** Wrap's work is what surrounds the commit — deciding what the conversation produced, its record and sources, briefing the writers, settling their returns — and a forge session needs none of it, being closer to developing a program, where committing each change is the practice: the forge wiki is public, so it keeps no record; a decision is recorded with the change it governs, or in a forge ledger while its work is in flight (forge mode); and a test-bed page a trial writes is committed as forge work, which ends in a commit rather than wrap (`D19.3`). A whole-tree stage in the program's own repo would also sweep program changes into one commit. Odin's save-bar clause still invokes wrap there, and wrap stops in a line, explicitly not a forge exception in the always-loaded `odin.md`. **Explicitly not a line in forge mode telling a session to record decisions as they settle**: its opening already says the ledgers hold in-flight decisions, which reach it and the catalog as their work settles, and `forge-mode.md` § *How it is grounded* says what a decision records.

The settings are shown as one block, explicitly not walked through. **A wiki inside another repository is asked about, standalone or nested, explicitly not refused**, which would block a vault kept whole in git, **and explicitly not committed into the outer repository**, where wrap's whole-tree staging would sweep in the vault's other folders. Nested, the outer repository sees an embedded repository and its own commits stop covering the wiki, which init says and never fixes, since the outer repository is outside the wiki (`D3.2`).

An anchor is a heading or a fact or decision id, never a label of the reviewer's own, which a second run cannot reproduce, so `marks` rejects an anchor its file does not hold. A content run covers a page only when its scope is the page's subject, the first segment of its path from the wiki root, **explicitly not a topic run that may have read it**, since a ledger's name gives its scope and not the pages a topic reached. **In the harness review *not yet* is a plain deferral, listed for five runs and dropped, explicitly not taken out of its vocabulary**, the user's call: a change is never walked twice, so nothing there recurs. **`marks` is a mode of `review-status.sh`, explicitly not a script of its own**: it reads ledgers by the names `ledger` mints, so one script holds the naming both depend on. **Explicitly not one mechanism with deprecating a fact**: a fact's trigger is a session reaching for it, which no script counts. **Never exercised on real data**: no *not yet* has been recorded by a real run, so promotion, expiry and deferral rest on the script's tests alone.

#### D18.1.2 — a place fixed three times is marked *redesign*

**A system-review place dispositioned *fix* three times or more since its last *redesign* is marked *redesign* by `marks` in place of *before*, explicitly not in place of *held* or *promote*, which a *not yet* keeps, and its finding proposes a redesign at any rank, explicitly not another patch; explicitly not left to the reviewer's notice, and explicitly not limited to the first two ranks.** Patching per run was previously observed going on with a reviewer's rule to propose otherwise in place: by review 18 the dispositions held 68 places fixed three times or more, the content review's walk 19 times and wrap's *Place it* 16. **`marks` holds it, explicitly not `check-system.sh`**, which reads the program and never the review records, and would raise every such place on every run, where `marks` raises only a place this run found wrong again. **A *redesign* disposition restarts the count**, explicitly not a count over all history, which would mark a place already redesigned on every later finding. **Any rank**, since the place fixed most often was a docs section, the lowest rank, fixed 22 times before it was rewritten. **Three fixes, explicitly not one**: a single earlier fix may have been to an unrelated part of the place, and recurrence is the evidence, as a re-raise is for *not yet* (`D18.1.1`). **Fixes count from the dispositions file's start, explicitly not from this decision's date**: the counts already there are the evidence the mark exists to surface. **The system review only, explicitly not the harness review**, whose findings do not recur (`D18.1.1`), **and explicitly not the content review**, whose fixes are to a wiki's pages, not a procedure patched per run. Whole-file places count as sections do, explicitly not exempted, though a script's fixes may be unrelated: the mark is a proposal the user can decline.

### D18.2 — session start shows how long since each review ran

**Session start shows one line of how long it has been since each review last ran — system and content in days, content with the scope its last run covered, harness in versions — explicitly not a count of commits, explicitly not a due threshold, explicitly not staleness, and explicitly not in the model's context.** The reviews have no cadence: what one has to find depends on how much the system was used and for what, so a threshold would be a guess. Neither days nor commits measure that — commits can be edits to the same few pages, and even those may leave one ready to split — but the user knows how much and how they have used the system and is less aware of how long it has been, so the line gives the part they lack. Harness is the exception because its review reads the releases since the checkpoint, not the user's use. **A content run of any scope counts as the last one, its scope shown**, explicitly not only a whole-wiki run. **A whole-wiki scan is not counted, explicitly not given a ledger so that it could be**: it writes nothing, since a candidate is not a finding (`D14.2.2`), and a group it surfaces counts once it is reviewed as a topic. The line is a reminder that the reviews exist, and it is fine for it to be ignored most of the time, so it is always shown rather than only when something is due. Staleness stays out on `D15.1`. **The content part shows in every session, and the system and harness parts only in a forge session, read from `session.kind`, explicitly not whichever ledger folders exist**: those two reviews run only in a forge session, and a user layer pointing their ledgers at an absolute store would otherwise put the program's review ages into every wiki session. **It shows at `startup` alone, explicitly not at `clear` too**: sessions were previously observed beginning with `/clear` more often than not, but on `clear` the harness shows the user nothing a `SessionStart` hook emits (`F10.2`). It goes out as a `systemMessage` (`F10.2`, `F10.3`), explicitly not hook stdout, so it costs the model nothing and gives the session nothing to raise unasked, and explicitly not exit-2 stderr, which shows as a hook error carrying the hook's command; its own hook group keeps that output apart from the resolver's stdout, which is meant for the model. **A status line is not shipped**, since a project's `statusLine` overrides the user's own, and it was previously observed not rendering in the desktop app's Code tab; `review-status.sh` prints the bare line for anyone who wants it in theirs. Reading ledger names is not a run reading its ledger back (`D18.1`): nothing filters what a review reports.

### D18.3 — each review writes where its own key says

**Each review writes where its own key says, `review.content.ledger_location`, `review.system.ledger_location` or `review.harness.ledger_location`, explicitly not one key with a folder per review under it**: content ledgers name a wiki's pages and are tracked with that wiki, save in a top-level dot folder other than `.yg/`, `.claude/` or `.sources/`, which a wiki's `.gitignore` ignores whole (`D12.1.10`) — **except the forge wiki's own, which the program gitignores, explicitly not tracked as an external wiki's are**, since the forge wiki is the public program and a disposition's reason is the conversation behind it; **an external wiki made public is asked where its ledgers go when it goes public (`D12.2`)**, explicitly not a default driven by `wiki.visibility`, which builds in that the owner wants them private, and explicitly not left to the owner unprompted, which publishes the reasons silently — while system and harness ledgers describe the program, so a user-layer override of one shared key would move every wiki's content ledgers out of their wikis too. A key is a path relative to the wiki root, absolute, or `~/`, **explicitly not an enum**: an absolute path takes the ledgers out of the repository and gives every checkout one store. `none` writes neither ledger nor dispositions.

#### D18.3.1 — the path comes from `review-status.sh ledger`

**The path a ledger is written to comes from `review-status.sh ledger`, explicitly not the resolution written out in each review and explicitly not one review pointing at another's**: three copies of the same steps were a drift risk, and a review is read alone. It is a mode of `review-status.sh`, **explicitly not a script of its own**, because the session-start line already finds the ledger folders to find the latest ledgers, and one reader keeps the relative, absolute and `~/` resolution in one place. It dates the name and takes the next free letter. **A missing absolute or `~/` folder is refused, explicitly not created**, since a mistyped path would start a second store silently where a refusal fails at the write; a relative one is created, being inside the wiki, **save one git ignores in a linked worktree, which is refused too, explicitly not created**: `git worktree remove` takes it with the worktree without a word about ignored files, and no other checkout reads it, so it is a second store as well; a tracked one goes with the worktree's branch, and the main checkout's stays where the next run looks. **Explicitly not redirected to the main checkout's folder**, which would have a review write outside the checkout it runs in. A missing key refuses too rather than reading as `none`, since it means a wiki with no resolved config. `~/` is expanded by each reader of the key, **explicitly not by the resolver**, whose values stay literal for every key.

#### D18.3.2 — pointing the ledgers outside the wiki moves what is committed

**Pointing the ledgers outside the wiki moves what is already committed into the new folder and untracks it, explicitly not leaving it in place**: history publishes it either way, but the tip then matches the answer, and `marks`, which reads only the folder the key names, keeps its dispositions history.

##### D18.3.2.1 — the folder must be empty

**The folder must be empty, explicitly not any folder that exists**: another wiki's same-named ledgers would be overwritten by the move, and going private's move out of it would take them too.

#### D18.3.3 — going private moves them back only into an empty folder

**Going private moves them only into an empty folder, explicitly not into one already holding files**, on the same ground: another wiki's ledgers there would be overwritten.

### D18.4 — the system and harness reviews never commit their ledgers

**The system and harness reviews never commit their ledgers, wherever the key puts them, explicitly not in the same commit as what was applied, as the content review does**: neither applies anything (`D16.1`, `D17.2`), their fixes are forge work taking their own commits, and a disposition's reason is the conversation behind it.

## D19 — Checking a change against the program

### D19.1 — the integration review runs on a diff from a base, fixing what is accepted

**The integration review runs on a diff from a base, `HEAD` by default, and fixes what the user accepts in the same change — explicitly not before the edit on a described intent, explicitly not a ledger, and explicitly not findings-only as the system review is.** The diff is concrete and names what it touches, where a described change is only a search. A base can be given for committed work, since the largest yields were previously observed on runs over a whole effort's commits. `D16.1`'s ground for never fixing is a finished corpus gaining words in answer to a finding. Here the change is still open, and a file left saying the old thing is the change unfinished, not a new defect. **A finding declined because the old text is meant to stand goes to the catalog entry the change touches, as its rejected alternative, and where it touches none, settled at the rule as `D1.1.1.1` settles an ignore, explicitly not a catalog entry minted for it**: a decision made only to keep old text is settled at that text, where its next reader meets it and a review no longer raises it.

**The diff takes the three program folders and the root's `.gitignore` and `.gitattributes`, by path, explicitly not the folders alone and explicitly not `check-system.sh files program`.** The two root files change how the program behaves — `.gitignore` keeps review ledgers out of public commits (`D18.3`), `.gitattributes` keeps scripts LF on a fork — so a change to either alone would otherwise end as nothing to review; `LICENSE` and the README change nothing the program does. Paths rather than the set, because a set cannot list a file a change deleted (`D19.3`).

### D19.2 — two Tyrs read the prose whole between them

**Two Tyrs read the prose whole between them, split by size, and the session merges their findings — explicitly not one reader, explicitly not a filter that decides relevance before reading, explicitly not a dependents script, and explicitly not the session inline.** A file can rest on how the program behaves without naming what changed, and only reading bodies reaches it. Each file's verdict depends on the change and not on another file, so the read partitions, each reader holding half the corpus rather than all of it, and the one cross-file judgment is the session's. **A changed file in neither reader's list, such as a script, goes to reader one, explicitly not left out of both**: the misstate test reads only a reader's own items, and a script's header comment is its working file (`D1.1.1`), so a change to one can leave its own prose saying the old thing. **The diff reaches the readers as a file, explicitly not pasted into each brief**, so each reads the change itself rather than a transcription. **Findings rank contradict, then misstate, then dangle, then lack**: a reader acting on the old behaviour first, a claim the change itself adds that what it names says otherwise next, a reference that fails when followed after, a gap the change's author is best placed to judge last. **A line the change adds is read against only the file, fact or decision it names, explicitly not against `facts.md` and the catalog whole**, which would add most of a hundred thousand tokens to each reader on every change; the wrong new claim was previously observed as most of what the system review later found fix-induced, the readers having read every file but the diff's claims.

### D19.3 — forge mode names when it runs, and the pre-commit hook gives a notice

**Forge mode names when the review runs, and the program's pre-commit hook prints a notice on the part a script can see — explicitly not a wrap check, explicitly not a hook that dispatches, and explicitly not a review-coverage check.** Forge work ends in a commit and does not run wrap, so the commit is the backstop's place. **The notice fires on a commit that adds, deletes or renames a file under `.yg/`, `.claude/` or `.claude-plugin/`, or edits the catalog, explicitly not on a file `check-system.sh files mechanism` lists**: `D4.1.1` makes those three folders the program, so a deleted file, which no set can list once it is gone, and a file in a new folder, which no set names yet, are both caught by their path. Forge-wiki pages never draw it. It runs after the leak check, so a refused commit prints none; it never refuses; and it skips a merge, which stages whatever the merge brought in, while the leak check still runs on one. A behaviour changed in place is the forge-mode line's and the user's. A coverage check asking per change whether any review would catch it failing was previously observed answering *worth covering* twice and *not worth covering* never, over 28-plus runs; its concrete case, a file no review reads, is `check-system.sh`'s row for a file in no corpus set. **The notice names its base as the commit `HEAD` is when the hook runs, explicitly not `HEAD~1`**, which is the flagged commit's parent only while that commit is still `HEAD`. Under `--amend` that is the commit replaced, so the review reads the amended-in change alone, explicitly not a clause in every notice for that rare path (`D2.2`).

## D20 — Replacing a part

### D20.1 — a part gets a seam where replacing it is expected

**A part gets a seam — a config key naming an implementation, a written contract with a version, and a conformance test — where replacing it is expected, not merely possible: it wraps something outside the program, of which alternatives exist and owners reasonably differ on which (`D2.1`) — explicitly not every part a fork might replace, and explicitly not left mouldable, edited in place when someone wants something different.** A fork that edits a shipped file turns every later upstream commit to that file into one it cannot apply, only recreate by hand; with a seam, its replacement is a config line and a file of its own, and only a commit that changes the contract needs that treatment, which the version makes visible. Ease of swapping is not the ground: moulding with an LLM is cheap either way, and it was previously the reason given for no seam. A fork may replace anything, so *a part a fork may replace* drew no line against building for cases nobody has; both seams so far pass the test, the transcription engine and the index backend. **Built as each part is next changed, explicitly not all at once**, since each costs a contract, a version and a test to keep.

#### D20.1.1 — transcription's contract is audio in, `segments.tsv` out

**Transcription's contract is audio in, `segments.tsv` out, explicitly not SRT and explicitly not JSON.** SRT has no speaker field, and a speaker label smuggled into its text is counted as words and lands mid-paragraph; JSON would put `jq` under a POSIX renderer, where each adapter can convert its engine's own form with whatever tools it holds. **Timestamps and speakers are declared capabilities, explicitly not requirements**, since engines exist with neither, and a requirement is the contract limiting which engine can be used. **What the flow can check stays in the flow, explicitly not left to the engine**: engines fail as success — cut short, stretches dropped, empty on speech, looping — so non-empty, density and repetition are checked whatever the engine, and gaps (an uncovered end among them) wherever the adapter declares timestamps, and the adapter declares only what the flow cannot see, `silence_safe`. **All but non-empty report, explicitly not refuse**, since a heuristic discarding minutes of engine time costs more than a flagged file the reader decides on; **gaps and repetition read engine output only, explicitly not a caption track**, whose gaps are the recording's music and silence. **An adapter's status is one of a closed set, explicitly not the engine's own passed through**, which lands on the flow's numbers and means something else — whisper-cli's 3 for a speech model that will not load (`F20.5`) read as a missing dependency. **Consent is a status and a token, explicitly not a download flag**, so a download, a spent credential and audio sent off the machine are one route.

#### D20.1.2 — a seam's form follows who calls it

**The seam's form follows who calls it.** A script-called seam is an executable in a directory per kind, named by config, explicitly not an MCP server, which only the model can call, so the flow would pass through a model turn and the result through its context; and explicitly not a command on PATH named in config, which works but is unversioned with the fork and out of reach of the conformance test, where a directory adapter can be a shim to one. A model-called seam, such as `index.query_provider`, is where MCP fits; its tag names a subagent or an MCP tool, a name and never a path, explicitly not a `command:<path>` form, on the script-called seam's ground: a path in config is unversioned with the fork and out of the conformance test's reach; that one has its key and not yet a written contract, version or conformance test, explicitly a gap rather than a second form of seam.

##### D20.1.2.1 — a script-called adapter is looked up in the user's folder, then the program's

**A script-called adapter is looked up first in the user's `${XDG_CONFIG_HOME:-~/.config}/yggdrasil/engines/<kind>/`, then in the program's `.yg/engines/<kind>/`, and config names it by a name, never a path — explicitly not a per-wiki `.yg/engines/`, and explicitly not shipped adapters only.** A per-wiki folder would make pulling a wiki bring code the program runs, and which engine runs is a fact about the machine, not the wiki. Shipped adapters only would leave a person who doesn't fork nothing to plug in. A fork versions its adapter by adding it to its program copy; the user directory is unversioned unless the person keeps it in their own dotfiles. A personal adapter of a shipped name shadows it.

##### D20.1.2.2 — an adapter takes the program and wiki roots as arguments

**An adapter receives the program and wiki roots as explicit arguments, explicitly not an environment variable**: no script of the program reads an environment variable the program defines, and an adapter in the user directory cannot find the program from where it sits.

#### D20.1.3 — a contract is closed in what it requires, open in what it carries

**A contract is closed in what it requires and open in what it carries**: an unknown key is ignored, so an implementation can carry more than its caller reads yet, and a later caller can start reading it with the version unmoved, the version moving only for a requirement. The open part is keys, explicitly not free prose, since the receiver has to parse it and an engine's or service's prose is a third party's text reaching the session.

##### D20.1.3.1 — an open part per direction, not every channel

**An open part per direction, explicitly not every channel**: an adapter's stdout stays the protocol's own lines, keys or not, since whatever reaches it can reach the session; what an implementation carries beyond the contract goes where the caller parses it, such as transcription's `meta.conf`.

#### D20.1.4 — a contract states what the caller needs

**A contract states what the caller needs, explicitly not one implementation's behaviour or default**: the first contract is written while one implementation exists, whose quirks then read as the general case, as transcription's did when it said an absent language hint meant explicitly not English, after whisper-cli's default.

#### D20.1.5 — shipped prose gets no seam

**Shipped prose gets no seam, explicitly not an override layer for forks and explicitly not pull machinery to merge one with a later version**: a rewording is not a second implementation behind a contract, so there is nothing for a key to name or a test to check. The cost a seam saves, a later commit the fork recreates by hand, is accepted for prose: combining a fork's rewording with the program as it moves on is the forker's to do, with their own Claude Code.

## D21 — Checking a page's frontmatter

### D21.1 — seven YAML indicators are banned by house style where they parse

**Seven YAML indicators are banned by house style where they parse, explicitly not because the parser rejects them.** A closed quoted value, a bare `|` or `>` opening a block scalar, and a value leading with `-`, `?` or `:` directly followed by text all parse cleanly — `F15.1` names the forms that fail or lose content, and these are not among them. They are refused anyway, because a quoted or block-scalar value in a vault of otherwise-plain frontmatter reads as significant when it is not, a leading `-` or `?` voids the block once a space follows it, and because the two classes must not be conflated: a detector built on *the parser rejects these* would be wrong about all seven, and a reader who found out would rightly distrust the rest. `.yg/bin/check-vault.awk` says *parses cleanly, but banned by house style* for exactly this reason.

## D22 — Credentials

### D22.1 — a credential is held as a reference, expanded inside the command that spends it

**A credential is held as a reference and expanded inside the command that spends it, explicitly not stored, and explicitly not built until something needs one.** Scaffolding for a consumer that does not exist earns nothing, and nothing here spends a credential. What follows is so it is not re-derived when something does.

**Two properties, and the second is the one that gets lost.** The system never stores the value, *and* the value never reaches a model's context. The live failure is the first without the second: nothing is stored, but a session runs the dereference on its own, reads the output, and passes it on. A value that reaches a transcript cannot be taken back, which is what makes this a floor rather than a preference.

**The expansion rule is the whole of it.** A reference expands *inside* the command that spends it, or into a pipe that command reads. Running the dereference alone — `printenv`, `cat` on a key file, a password-store `show` — is exactly how the value lands in the transcript, and it is the natural thing to do.

#### D22.1.1 — a command over a variable, and a tool holding its own auth over both

**Shape.** A tagged reference in config: a variable name, or a command whose output is the value. A file path form collapses into the command form and earns no token of its own. **Prefer a command, explicitly not a variable where a command will do**, because an unset variable expands to empty and exits 0, so an unresolved reference is indistinguishable from a resolved one and the request goes out unauthenticated. **Preferred over both: a tool that holds its own auth**, where nothing is dereferenced at all.

#### D22.1.2 — one key per service, never per flow

**One key per service, explicitly not per flow.** The credential belongs to the service it authenticates to, and every operation against that service reads the same key whatever the verb — a flow growing another verb changes nothing about what is safe. A shared pool was rejected because it removes the restriction that actually binds: a key is expanded only in a command talking to its own service. **The use site is the enforcement, not the key name.**

#### D22.1.3 — kept out of `argv`, piped in on stdin

**Keeping it out of `argv`, explicitly not interpolated into a command's arguments.** A value interpolated into a command's arguments is readable by any local account for the life of the process. Pipe it in on stdin instead. Two things make that safe rather than merely different: `printf` is a shell builtin, so the pipe does not relocate the value into another process's arguments, and a temporary file, if one is used, is created private. Watch the collision — a tool reading its header from stdin cannot also read a body from stdin, and the second read silently gets nothing rather than failing.

#### D22.1.4 — never in a URL

**Never in a URL, and the reason is the far end, explicitly not the client's own output.** The server logs it permanently and its error body often echoes a rejected key back. This is not fixed by suppressing client-side output. On the return path take the status code rather than the body, keep error text off stderr, and avoid every verbose or trace flag — each prints the request line, the headers, or the full query.

### D22.2 — recognise and redact by shape, never by the value

**Recognise and redact by shape, explicitly not by matching the value.** You cannot match a value you are not permitted to hold, so anything working by comparison against the secret is ruled out by construction.

#### D22.2.1 — a shape is a label, not a format

**A shape is a label, explicitly not a format.** Match the syntax that marks a value as a credential — a `Bearer` prefix, an `api_key` / `apiKey` / `token` / `password`-style key name, a connection string — rather than a vendor's key design, a distinctive prefix, or an entropy test. Key names outlive key formats, so a label-based rule rots far more slowly than a list of vendor shapes. It is incomplete by construction, and a payload using its own key name needs that name adding.

#### D22.2.2 — an unknown body is surfaced as a characterisation

**Where a body's structure is unknown, surface a characterisation of it, explicitly not the body redacted and surfaced.** That is the only safe handling of a shape nothing recognised.

### D22.3 — the gate is the session's

**The gate is the session's, explicitly not a script's or a dispatch's, because only the session has a user to ask and can run the checks.** Before a write recording access to a service, or a step that spends one: establish whether the target path is tracked, ignored, or new-but-not-ignored; say plainly whether this ends up committed; and confirm for *this* write to *this* location. **A repository with no remote is not a safe state** — the value still enters history permanently, and a remote added later exposes it retroactively. A key written into config needs the config re-resolved in the same act, or the session that just recorded the access spends the rest of its life reporting there is none.

### D22.4 — a credential that arrives is containment, not prevention

**A credential that arrives rather than being passed is containment, explicitly not prevention.** Once a raw value is in the transcript the protection is gone; the gate can stop it being committed and cannot unsay it. Say so, write it nowhere, offer the reference route. No detection is built for this. That is a gap, not a considered rejection.

### D22.5 — the version-fragile half is kept apart from the rule

**Keep the version-fragile half separate from the rule, explicitly not mixed into it.** The invariants above do not move; the exact flags and forms that satisfy them are stamped against a tool version and expire. Splitting them lets the fragile half be re-probed without touching the floor.

## D23 — What waiting on a script costs

### D23.1 — a script the user waits on is timed, and records a `Cost:` line

**A script the user waits on is timed at several sizes of each input it loops over, and records the result, or why it is not timed, in a `Cost:` line — explicitly not a complexity-class rule, explicitly not a self-timing warning or a fixed time budget, and explicitly not a review pass.** The cost that matters is how long the user waits, so a script nobody waits on — a background dispatch, a review started knowing it takes a while — is not held to it; and the input that keeps growing is the wiki, which outgrows the program's own files in use. Both scripts previously found slow were linear, a process started per page, so a complexity rule would have passed them, and that shape is one of many where a measurement catches any. The ratio between sizes holds on any machine and an absolute time does not, which rules out a warning past a cap and a budget in milliseconds: tuned on one userland it fires falsely on another, and a warning that can name its fix should apply it instead. Whether the line is there is enumerable, so `check-system.sh` reports its absence. Whether its reason still holds turns on callers in other files, and what changes it is a forge edit adding a caller, so forge mode carries that rather than a review pass of its own.

## D24 — How facts and decisions are recorded

### D24.1 — a record's id carries its place in the tree

**A record's id is its group's number with a part added for each level below it, and each level narrows the one above — explicitly not stable flat ids under topic sections, and explicitly not an entry filed under one it is merely related to, which is its sibling.** The top level is a heading, explicitly not a fact or a decision, so every citable id has two parts at least (`F3.1`, `D2.2`): grouping is itself a form of narrowing, so one rule runs the whole tree. Flat ids never need renaming, but the group in the id is what keeps like rules together, which is what nesting was asked for. **Decisions nest as facts do, and an overgrown one is split into rulings at the paragraph or the bullet, explicitly not an id for every bold clause**, which multiplies citations without telling a reader more. **Both files nest by heading level, explicitly not the catalog's bold paragraphs with the depth in the id alone, and explicitly not one heading per group with the entries as nested bullets**: headings read best in both, and bullets put an entry's own list at its children's indent.

#### D24.1.1 — moving a record renames it, through `rename-ids.sh`

**A rename is a script kept with its test, `rename-ids.sh`, explicitly not a one-off**: misfiling recurs, every correction is a rename, and a rename's failure is silent, a citation left on the old id still reading fine beside the wrong entry (`D2.1`). It matches whole ids, looks every match up against the map as written so a shift or a swap never renames twice, and takes further files and folders, so open ledgers, unconsumed handoffs and review dispositions are rewritten in the same run without the program naming where they live. **A split whose lead stays the parent sends the citations there, which is never wrong, only imprecise; a split into siblings has no parent to send them to, its group being uncitable, so the run refuses until each is pointed at one half by hand, explicitly not all sent to one half**, which leaves a citation of the other half pointing at the wrong entry and reading fine. The system review's facts-to-files pass raises a citation resting on a parent where a nested entry is the claim.

#### D24.1.2 — no map of old ids, no register of retired ones, no rule against reuse

**No map file of old to new ids, no register of retired ids, and no minting rule against reusing one, explicitly not "next above the highest ever used"**: `check-system.sh` reports every citation of an id that does not exist, on every run, and closed history, old commits and closed ledgers, keeps its ids and is read against the catalog at its commit (`git show <sha>:.yg/forge-catalog.md`), which is rare, visible and easy (`D2.2`). Reuse bites only where a rename missed a citation and that exact id is later reissued, leaving the citing sentence beside an unrelated entry, which a system review catches: facts-to-files tests a citation against its fact, and for decisions the double rarity covers it.

### D24.2 — the system review's structure pass judges placement

**A structure pass asks whether each entry narrows its parent and sits in the group it belongs to, a pass of judgment, explicitly not a script**, and no other pass covers placement. **It proposes a move only where the current place is wrong, explicitly not where another is marginally better**: each move is a rename, and an entry with two plausible homes would otherwise flip from run to run. **No tie-break for such entries is written ahead, explicitly not a rule drawn from the cases settled when the tree was first filed**: one is written only if the review keeps raising two-home placement, as the fix for a recurring finding (`D2.2`).
